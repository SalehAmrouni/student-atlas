# Security

## Design

- **Static by design**: production is plain static files plus small functions for reviews (`api/reviews.js`, `api/reviews-admin.js`), accounts and rooms (`api/account.js`, `api/rooms.js`), and College Lab AI feedback (`api/college-lab.js`). Everything else has no server code.
- **Reviews**: input is validated and length-limited on the server, control and bidirectional characters are stripped, and contact details, links, and social handles are refused. Requests must be same-origin JSON under 4 KB. Visitors are identified only by a salted SHA-256 hash of their IP, used for rate limits, one review per opportunity, and report counting; the hash is never returned by the public API. Flagged and reported reviews wait in a moderation queue. Storage credentials (`SUPABASE_SECRET_KEY`) and `REVIEWS_ADMIN_TOKEN` live only in Vercel environment variables. The moderator token is compared in constant time, and repeated wrong tokens are rate limited.
- **College Lab endpoint**: `POST /api/college-lab` calls the Claude API only when `ANTHROPIC_API_KEY` is set in the host's environment (never committed). Requests are schema-validated with size limits, cross-origin browser requests are rejected, each instance applies a per-IP rate limit (`COLLEGE_LAB_RATE_LIMIT`, default 30 per 10 minutes), responses are `no-store`, and essays, transcripts, and questions are never stored or logged (errors log only the task and status code). Student-provided text is wrapped in tags and the prompts tell the model to treat it as data. Set a monthly spend limit on the Anthropic key as a backstop.
- **Database (Supabase Postgres)**: tables live in an `atlas` schema that Supabase's Data API doesn't expose, with row-level security on for every table and no policies. The `anon` and `authenticated` roles have no rights on the schema, its tables, or the `public.atlas_*` functions; only `service_role` does. The server calls those functions over HTTPS with the secret key, which is read from the environment by the functions in `api/` and never sent to the browser. Every function sets an empty `search_path`, and the server only calls function names matching `atlas_*`. Tests run the real migrations (PGlite) and check that row-level security is on and the API roles have no access.
- **Headers**: `vercel.json` (and the local dev server, from the same `server/headers.js`) sets a strict Content Security Policy (`default-src 'self'`, no inline script or style, `frame-ancestors 'none'`), `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, `Permissions-Policy`, and HSTS. Tests keep the two in sync.
- **No third-party code at runtime**: icons are bundled locally; no CDNs, analytics, or trackers.
- **Output safety**: the browser builds all dynamic UI with `textContent`/`createElement`. Zeus's replies go through a Markdown renderer that never parses HTML and only allows `http(s)` links and `opp:` references to known ids.
- **Data validation**: every opportunity is validated against a strict schema (`https` links only) at build time.
- **Zeus guardrails**: Zeus runs locally and only recommends entries from the directory. It points students to 988 and 911 when it detects crisis language, redirects inappropriate messages, and discourages sharing contact details.
- **Accounts and rooms** (`api/account.js`, `api/rooms.js`, `server/accounts/`): anonymous random usernames with a 10-character sign-in code stored as a salted SHA-256 hash. Sessions are 32-byte random tokens in an `HttpOnly; SameSite=Lax; Secure` cookie; only a hash of the token is stored. POSTs must be same-origin JSON. Login failures are rate limited per IP and per username. Teacher access uses a token derived (HKDF) from a 160-bit teacher key generated in the teacher's browser; the server stores only its hash and compares in constant time. Real names are encrypted client-side with the room's RSA-OAEP public key; the private key is stored only wrapped with an AES-GCM key derived from the teacher key. Teachers receive a filtered view (no chats, essays, transcripts, tracker notes, exact family finances, or unshared Overcoming obstacles text). Data expires after ~13 months of inactivity. **Limits:** progress data is stored in plain form under the username and could identify a student in context; this design reduces but does not remove a school's FERPA/COPPA obligations.
- **Privacy (without an account)**: no cookies. Profiles, saved lists, College Lab work, and chats stay in the browser. College Lab sends an essay, transcript text, or mentor question (with the stats the student entered) to Claude only after the student opts in, and only when they press a button; with AI off or unconfigured, everything runs on-device. Reviews are public and contain only what the reviewer types. Resource suggestions are sent only when the person chooses to open the pre-filled GitHub issue (which is public), and the form collects no personal information.

## Reporting a vulnerability

Please open a private security advisory on the GitHub repository rather than a public issue.
